## 1. 引言

### 1.1 编写目的

本文档描述遥测平台两项新功能的功能设计：**版本运营视图**与**归因管理面重建**。内容围绕三项展开：解决什么问题、提供什么能力、如何验证。存储结构、接口定义、页面实现等细节不在本文范围，待功能设计评审通过后另行输出详细设计说明书。

预期读者：管理人员（需求方）、开发人员、测试人员、审核人员。

### 1.2 项目背景

- 软件系统名称：AAW 遥测平台（telemetry-server、遥测门户、遥测管理台）
- 所属项目：Awesome-Agent-Workflow（AAW）
- 用户：团队带头人与平台管理员（主要）、全体 AAW 使用者（间接受益）
- 与其他系统的关系：归因结果依赖外部归因引擎（部署于保密环境，本平台通过服务调用获取结果）；本设计不涉及归因引擎内部改动。

### 1.3 用户反馈的问题

| 编号 | 反馈 | 现象 |
|---|---|---|
| P1 | 不知道谁还在旧版本 | CLI 版本随遥测入库，但页面上既无版本筛选，也无"人 × 版本"视图，推动升级时找不到目标人 |
| P2 | 采纳率分母失真 | 大量生成代码不以合入为目的（实验、探索、本地工具），或从未上传补丁进入归因；这些行数全部计入采纳率分母且永远不进分子，采纳率被系统性低估，人员排序失真 |
| P3 | 超窗归因无法补救 | 工作流常长时间暂停后继续，MR 可能在开发完成很久后才合入；超出重试窗口（默认 90 天）的记录被自动置为失败，管理员无法在页面上补跑 |
| P4 | 归因记录定位困难 | 开发者申诉"合入了却没匹配上"时，管理员无法按人/仓库/需求/MR 快速找到那条记录并查看判定依据 |
| P5 | 故障后失败堆积难处理 | 归因引擎故障期间产生的失败记录只能逐条手动重试，无法按失败原因圈定后批量处理 |
| P6 | 归因排队情况不透明 | 只能看到状态计数，分不清哪些在正常等待、哪些已卡死需要人工介入 |

### 1.4 术语与缩略语

| 术语/缩略语 | 定义 |
|---|---|
| 开发记录 | 一次开发步骤的完整执行记录（含代码统计与补丁信息） |
| 归因 | 将开发记录生成的代码与最终合入的 MR 进行匹配、计算采纳行数的过程 |
| 未入队 | 开发记录已完成但从未进入归因流程（补丁未确认上传，不存在归因结果） |
| 无关化 | 管理员将开发记录标记为"不参与采纳统计"的操作，可恢复 |
| 强制重跑 | 管理员绕过重试窗口限制、重新发起一次归因的操作 |
| 合入意图口径 | 采纳率的一种统计口径：分母仅计未被判为无关的生成代码（详见 4.5） |
| 非发布版本账号 | 上报版本号无法识别为正式发布版本的账号（多为冒烟/联调账号） |

## 2. 总体设计

### 2.1 设计目标

1. 管理员能直接回答"**谁还在使用旧版本**"，并推动其升级（对应 P1）。
2. 采纳率统计区分"为合入而生"与"非合入目的"的代码，管理员可治理分母（对应 P2）。
3. 超窗、失败、堆积的归因记录均可在页面上定位、补救与批量处理（对应 P3、P4、P5、P6）。

### 2.2 功能结构

```
遥测平台功能增强
├─ F1 版本运营视图（采纳看板）
│   ├─ C1.1 版本筛选
│   ├─ C1.2 旧版本使用名单
│   └─ C1.3 版本升级轨迹
└─ F2 归因管理面重建（管理台归因页签）
    ├─ C2.1 组合检索与定位
    ├─ C2.2 归因详情
    ├─ C2.3 未入队记录呈现
    ├─ C2.4 无关化与恢复
    ├─ C2.5 手动重跑与强制重跑
    ├─ C2.6 批量处理
    ├─ C2.7 失败分组与处理趋势
    ├─ C2.8 积压体检
    ├─ C2.9 调度器健康
    └─ C2.10 看板双口径采纳率（联动能力）
```

问题覆盖矩阵：

| 问题 | 由哪些能力解决 |
|---|---|
| P1 | C1.1、C1.2、C1.3 |
| P2 | C2.3、C2.4、C2.10 |
| P3 | C2.5 |
| P4 | C2.1、C2.2 |
| P5 | C2.6、C2.7 |
| P6 | C2.8、C2.9 |

### 2.3 使用角色与入口

| 角色 | 入口 | 用途 |
|---|---|---|
| 管理员/带头人 | 采纳看板（门户） | 版本运营视图、双口径采纳率 |
| 管理员 | 管理台·归因页签 | 归因记录的检索、补救、无关化治理 |

### 2.4 设计原则与约束

1. **现有口径不破坏**：看板现有数字与口径全部保持不变，新能力一律以增量方式并列呈现，保证历史数据可比。
2. **治理操作可回滚**：无关化必须可恢复；批量操作有数量上限并提供执行前预览，防止误操作扩散。
3. **补救动作留痕**：管理员的重跑、无关化等操作在记录上留下可识别标记，事后可审计"哪些结果是人工干预产物"。
4. **不依赖归因引擎改造**：除一项外部确认事项外（见 §6），全部能力在遥测平台内闭环。

## 3. 功能块 F1：版本运营视图

### 3.1 解决的问题

版本信息已随遥测数据完整入库，但页面上不可见、不可筛、不可归人（P1）。管理员无法评估旧版本存量规模，也无法找到该升级的具体人。

### 3.2 提供的能力

**C1.1 版本筛选**

采纳看板筛选栏（现有组件/人员/时间窗旁）新增"版本"多选。选定版本后，看板全部图表（采纳率、趋势、人员产出、组件明细、工作流明细等）按所选版本切片。用于对比新旧版本的采纳率与使用行为差异。

**C1.2 旧版本使用名单**

采纳看板新增"版本运营"卡片，回答"谁还在旧版本"：

- 头部指标：窗口内活跃人数、其中已在使用最新版本的人数、仍在旧版本的人数、非发布版本账号数；
- 名单主表：人（姓名 + 邮箱）、当前版本、落后最新版本几个版本位、最近一次上报时间、累计上报次数、历史用过的版本数；
- 默认排序：落后位数多者优先、其次最近活跃者优先——待推动升级的人自动浮顶；
- 展示邮箱：该卡片面向管理员，"找到人"依赖邮箱。

**C1.3 版本升级轨迹**

名单行可展开查看该用户的版本时间线（每个使用过的版本的首末上报时间），区分"一直没升级"与"刚刚升级完成"两类人，前者才需要推动。

### 3.3 业务规则

| 规则 | 内容 |
|---|---|
| "还在用旧版本"的判定 | 以该用户**最近一次上报**所用的版本为准；历史上用过旧版本但已升级的人不算。按邮箱识别人（同一邮箱多个提交名的视为同一人，显示最近用名） |
| 统计窗口 | 默认近 30 天，可调；窗口内无上报的人不出现（不构成"还在用"） |
| 最新版本的基准 | 自动取自平台已发布的最新客户端版本，无需人工维护；发布信息缺失时以数据中可见的最高正式版本为基准 |
| 非发布版本账号 | 版本号无法识别为正式版本的账号不进入"旧版本"名单，单独计数（多为冒烟/联调账号，避免污染名单） |
| 统计范围 | 仅统计 AAW 主流程通道；测试通道的版本号为派生值，无运营意义，不纳入 |

### 3.4 验证方法

| 场景 | 准备 | 操作 | 预期 |
|---|---|---|---|
| V1-1 名单正确性 | 环境中存在：用户 A（近 30 天内上报、当前最新版）、用户 B（近 30 天内上报、当前旧版）、用户 C（三个月前用旧版后无上报） | 打开版本运营卡片 | 名单含 B（标记落后位数）、不含 C；A 计入"已用最新版" |
| V1-2 非发布版本隔离 | 存在上报版本为冒烟专用版本号的账号 | 打开卡片 | 该账号不出现在旧版本名单，计入"非发布版本账号" |
| V1-3 版本筛选联动 | 环境中存在至少两个版本的上报数据 | 筛选栏选定某一旧版本 | 看板全部图表数字随筛选变化，与该版本数据一致 |
| V1-4 升级轨迹 | 某用户先后使用过 3 个版本 | 展开该用户行 | 时间线显示 3 个版本及各自首末上报时间 |
| V1-5 口径核对 | 任意真实数据集 | 用名单结果与按 §3.3 规则编写的核对查询比对 | 逐人一致 |

## 4. 功能块 F2：归因管理面重建

### 4.1 解决的问题

现有管理台归因页签只有单一状态筛选和逐条重试，无法支撑：分母治理（P2）、超窗补救（P3）、申诉定位（P4）、故障批量恢复（P5）、排队健康度判断（P6）。

### 4.2 能力总览

重建后的归因页签按"体检 → 定位 → 处理 → 治理"组织：顶部为健康与积压概况，中部为可组合检索的记录列表，每行可展开详情并执行操作。

### 4.3 能力说明

**C2.1 组合检索与定位**

记录列表支持按以下条件任意组合筛选：仓库、人员、需求号（SR/AR）、MR 号、归因状态、结果状态（匹配成功/未匹配）、质量标记、算法版本、通道（主流程/测试流程）、入口类型、时间窗。申诉场景下输入 MR 号或人名即可唯一命中目标记录。

**C2.2 归因详情**

单条记录可展开查看完整判定依据：

- 归因结果：三档一致性（60%/80%/90%）的归因行数、置信度、结果状态；
- 匹配对象：MR 编号与链接、MR 合入时间、来源/目标分支、MR 总行数；
- 判定口径：归因算法版本、diff 规则版本（用于判断新旧算法结果并存）；
- 质量信息：全部质量标记、重试次数与下次重试时间；
- 关联开发记录：分支、代码构成摘要（生产/测试/脚本等分类行数）、补丁上传状态。

**C2.3 未入队记录呈现**

从未进入归因流程的开发记录（补丁未确认上传）以"未入队"状态出现在同一列表中，可按人/仓库/时间筛选。这是 P2 的主要工作面：管理员在此核对哪些生成从未走合入流程，并执行无关化。

**C2.4 无关化与恢复**

- 对象：管理员可将**未入队、已判定未匹配、已失败**的记录标记为"无关"（即不参与采纳统计）；
- 禁止：已匹配成功（有合入事实）的记录不允许标记；
- 要求：标记必须填写原因；
- 呈现：已排除的记录默认隐藏，可切换查看；
- 恢复：随时可撤销标记，统计口径随之复原；
- 批量：可按当前筛选条件批量标记，单次有数量上限并需预览确认。

**C2.5 手动重跑与强制重跑**

- 手动重跑：对失败/待重试记录重置归因（现状能力，保留）；
- 强制重跑：对**已超出重试窗口**（默认 90 天）的失败记录，管理员可在页面上强制重新发起归因，执行时二次确认；
- 留痕：强制重跑的记录带有"超窗补跑"标记，与普通重试区分，供事后审计；
- 保护：正在执行中的记录不可重跑。

**C2.6 批量处理**

按 C2.1 的任意筛选条件圈定一批记录后批量重跑（可含强制），执行前提供预览（将影响多少条、其中多少条因执行中跳过），执行后返回处理结果计数。引擎故障恢复后的典型用法：按失败原因圈定失败批，一键重跑。

**C2.7 失败分组与处理趋势**

- 失败原因分组：按失败原因类别（引擎不可达、引擎执行异常、归因执行失败等）汇总计数，每组提供"按此条件处理"入口；
- 处理趋势：近若干天的每日处理量、成功/未匹配/失败数量、平均置信度；
- 口径构成：按算法版本统计结果分布，暴露新旧算法结果并存的程度。

**C2.8 积压体检**

归因页签顶部呈现非终态记录的四分类：

| 分类 | 含义 | 管理动作 |
|---|---|---|
| 等待补丁 | 开发已完成、等待补丁上传 | 无需处理 |
| 等待调度 | 已入队、等待本轮扫描 | 无需处理 |
| 退避中 | 失败后按规则等待重试 | 无需处理 |
| 疑似卡死 | 早应被处理却长期停留，或执行超时 | 高亮提示，提供重跑入口 |

**C2.9 调度器健康**

归因调度器的运行状态（运行中/自暂停、上次扫描时间与处理量、连续失败次数、扫描间隔、重试窗口）内嵌在归因页签顶部，与"立即扫描"操作合并呈现，故障处理不再切换页签。

### 4.4 与现有管理台的关系

总览、注册表、日志三个页签保持现状；归因页签按本设计重建。现有手动重试能力保留并被 C2.5 取代包含。

### 4.5 看板联动：双口径采纳率（C2.10）

无关化的统计效果在采纳看板承接：

- 现有口径（**全量口径**：采纳行数 ÷ 全部生成行数）保持不变，仍是主数字；
- 新增并列的**合入意图口径**：采纳行数 ÷（全部生成行数 − 已无关化行数）；
- 两口径的差值百分比即"实验性生成占比"，作为独立指标展示；
- 总览、组件、人员三处提供双口径；趋势视图的双口径随后续阶段补充。

### 4.6 验证方法

| 场景 | 准备 | 操作 | 预期 |
|---|---|---|---|
| V2-1 申诉定位 | 造一条已知 MR 号的归因记录 | 在归因页签按 MR 号检索 | 唯一命中；详情可见置信度、三档行数、MR 信息、算法版本 |
| V2-2 强制重跑 | 造一条超出重试窗口的失败记录 | 先尝试普通重跑，再执行强制重跑（确认弹窗） | 普通重跑被拒绝并提示窗口已过；强制重跑后记录回到待处理并带"超窗补跑"标记，最终结果更新 |
| V2-3 无关化效果 | 造若干未入队记录并标记无关 | 对照采纳看板 | 合入意图口径分母下降相应行数、全量口径数字不变；"实验性生成占比"出现对应变化 |
| V2-4 无关化约束与恢复 | 一条已匹配成功记录；一条已无关化记录 | 对前者执行无关化；对后者执行恢复 | 前者被拒绝并说明原因；恢复后统计复原 |
| V2-5 批量处理 | 造一批同原因失败记录 | 按该失败原因圈定，预览后批量重跑 | 预览计数与实际处理数一致；执行中的记录被跳过并计入结果 |
| V2-6 积压体检 | 分别造出四类状态的记录 | 查看归因页签顶部 | 四分类计数正确；"疑似卡死"高亮并提供处理入口 |
| V2-7 通道区分 | 主流程与测试流程记录并存 | 按通道筛选 | 两类记录可分别查看，互不混计 |
| V2-8 留痕审计 | 执行过强制重跑与无关化的环境 | 查看对应记录 | 人工干预标记与原因、时间完整可见 |

## 5. 实施与验收计划

功能分五个阶段交付，每阶段独立可验收；F1 与 F2 无依赖关系，可并行。

| 阶段 | 范围 | 覆盖问题 | 验收场景 |
|---|---|---|---|
| 一 | C1.1 版本筛选 | P1 | V1-3 |
| 二 | C1.2、C1.3 版本运营卡片 | P1 | V1-1、V1-2、V1-4、V1-5 |
| 三 | C2.1、C2.2 检索与详情；C2.5 强制重跑 | P3、P4 | V2-1、V2-2 |
| 四 | C2.3、C2.4 未入队与无关化；C2.6 批量；C2.10 双口径 | P2 | V2-3、V2-4、V2-5 |
| 五 | C2.7、C2.8、C2.9 统计与体检 | P5、P6 | V2-6、V2-7 |

操作审计与管理台身份鉴别（V2-8 的完整形态）依赖鉴权方案落地，作为后续独立工作项。

## 6. 尚未解决的问题
